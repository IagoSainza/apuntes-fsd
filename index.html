Terminal (Unix)

Moverte por carpetas y gestionar archivos sin ratón. Antes de hacer algo peligroso: pwd y ls para saber dónde estás.

Lo esencial

  • pwd dónde estoy · ls qué hay aquí. Si te pierdes, estas dos.
  • cd carpeta entra · cd .. sube · cd ~ a tu usuario.
  • mkdir crea carpetas · touch crea archivos · cp copia · mv mueve o renombra.
  • rm borra para siempre (no hay papelera). rm -rf sin preguntar: cuidado.
  • Si un nombre tiene espacios, va entre comillas: cd "Trabajo clase".

Tu entorno de trabajo

  • Terminal (Warp o Git Bash): la ventana donde escribes comandos. En Windows se configura Warp para que use Git Bash, así los comandos son iguales que en Mac/Linux.
  • VS Code: el editor donde escribes el código. Extensiones recomendadas: Prettier + Format on Save (te ordena el código al guardar) y VS Code Icons (iconos para ver qué es cada archivo).
  • Node.js (versión LTS): permite ejecutar JavaScript en la terminal sin navegador: node archivo.js.

Git

Git guarda "fotos" (commits) de tu código. Un archivo pasa por tres sitios: carpeta de trabajo → staging (preparado) → commit (guardado) → y luego al remoto (GitHub).

Lo esencial

  • Un cambio pasa por: carpeta → add → staging → commit → historial → push → GitHub.
  • git status a todas horas: te dice en qué rama estás y qué falta por guardar.
  • Una rama por tarea: git switch -c feature/algo. Al acabar: push, Pull Request y merge en GitHub.
  • Antes de empezar: git switch main + git pull. Commits pequeños con verbo: "Añade…", "Corrige…".
  • Nunca git init dentro de otra carpeta que ya tenga Git. El repo del profe: solo git pull, no se toca.

El ciclo que harás siempre

editas código→git status→git add .→git commit -m "mensaje"→git push
git switch -c feature-login        // 1. creo rama nueva y me cambio a ella
git status                         // 2. ¿qué he cambiado?
git add .                          // 3. preparo todos los cambios
git commit -m "Login con JWT"      // 4. guardo una versión
git push -u origin feature-login   // 5. la subo (-u solo la primera vez)

Trabajo en equipo con GitHub

GitHub es la web donde se guarda el repositorio en la nube para compartirlo. Para conectarte se usa un token (PAT) en vez de contraseña.

Orden para no pisar el trabajo de nadie:

git fetch origin main→git pull origin main→git push origin main
  1. fetch: mira si hay algo nuevo en GitHub, sin tocar tus archivos.
  2. pull: lo descarga y lo junta con lo tuyo.
  3. push: sube tus commits.
  • Una rama por tarea (feature/login). No se trabaja directamente en main ni develop.
  • git checkout -b feature/login hace lo mismo que git switch -c: crea la rama y te cambia a ella.
  • Conflicto: dos personas cambiaron las mismas líneas. VS Code te deja elegir: Accept Current (lo tuyo), Accept Incoming (lo que llega) o Accept Both (las dos). Luego haces commit.
  • Nunca hagas git init o git clone dentro de otra carpeta que ya es un repositorio.

Diagrama: la rama de cada ejercicio

Línea de arriba: main. Sales de ella con una rama nueva (abajo), haces tus commits (puntos naranjas), la subes con push y vuelve a main con la Pull Request. Después actualizas main en tu ordenador.

Flujo de trabajo con una rama

Sirve para cada ejercicio o cada cosa nueva que hagas. Si lo sigues en orden, Git no da sorpresas:

  1. Partir de main actualizado: git switch main y git pull.
  2. Crear la rama del ejercicio: git switch -c feature/ejX-nombre. Si ya existe, sin -c.
  3. Programar por pasos y hacer un commit cada vez que un paso funciona: git add archivo + git commit -m "Verbo + qué hace".
  4. Si usaste IA, decláralo como lo pida el profe.
  5. Explicar lo que has hecho en el README antes de cerrar la rama.
  6. Comprobar: git status tiene que decir nothing to commit, working tree clean.
  7. Subir la rama: git push -u origin feature/ejX-nombre.
  8. En GitHub: Pull Request → Merge pull request → Confirm merge. No borrar la rama.
  9. Volver a main: git switch main y git pull.

git add archivo solo mete ese archivo en el commit. git add . mete todo lo que has cambiado. Lo que esté en verde en git status es lo que entrará.

Mensajes de commit: empiezan por un verbo en presente y dicen qué hiciste ("Calcula la media", "Corrige el saludo vacío"). Nada de "cambios" o "fix".

Gitflow: para qué sirve cada rama

  • main: solo versiones que funcionan (v0.1, v1.0…).
  • develop: donde se junta el trabajo del día a día.
  • feature: una rama por funcionalidad; sale de develop y vuelve a develop.
  • release: se prepara una versión; va a main y a develop.
  • hotfix: arreglo urgente desde main; vuelve a main y a develop.

Condicionales (control de flujo)

Hacen que el programa tome un camino u otro según una condición que da true o false.

Lo esencial

  • if / else if / else entra solo en el primer camino que se cumple.
  • Por eso la condición más exigente va arriba (≥ 9 antes que ≥ 5).
  • El else no lleva paréntesis: es "en cualquier otro caso".
  • if + if son preguntas independientes (pueden cumplirse las dos); else if es una sola decisión.
  • Sin ; detrás del if (...): si lo pones, el if no hace nada.

if · if/else

// if: solo se ejecuta si la condición es true
if (edad >= 18) {
  console.log("Eres mayor de edad")
}

// if/else: un camino u otro, siempre entra en uno
if (temperatura > 25) {
  console.log("Hace calor")
} else {
  console.log("No hace calor")
}

else if: varias opciones

if (edad >= 0 && edad < 18) {
  console.log("Eres menor de edad")
} else if (edad >= 18 && edad <= 110) {
  console.log("Eres mayor de edad")
} else {
  console.log("Valor no valido")   // -30, 123…
}
  • Se comprueba de arriba abajo y entra solo en el primero que cumpla.
  • Pon primero la condición más restrictiva y al final la más genérica.
  • El else final recoge "todo lo demás" (valores no válidos).

Diagrama: if / else if / else (ejemplo de notas)

Pregunta de arriba abajo y entra solo en el primer camino que cumple. Los demás se los salta. Por eso las condiciones más exigentes van primero. Al final, todos los caminos siguen por el mismo sitio.

Bucles (repetir código)

Un bucle repite un bloque de código mientras se cumpla una condición. Así no escribes lo mismo 100 veces.

Lo esencial

  • for (inicio; condición; paso): pregunta → hace lo de dentro → cambia i → vuelve a preguntar.
  • En la primera vuelta i vale lo del inicio; el paso (i++) se hace al final de cada vuelta.
  • Para recorrer un array: i < lista.length (no <=), y recorre la lista que estás procesando.
  • for…of te da cada valor, sin posición. Si necesitas la posición, for con i.
  • for…in recorre las claves de un objeto (name, race…). El valor se saca con obj[key].
  • Lo que va dentro del bucle se repite en cada vuelta; lo que va después, una sola vez.

  console.log(`Vuelta número ${i}`)   // 0, 1, 2, 3, 4

  • do-while: entra siempre al menos una vez y luego comprueba.

Funciones

Una función es un trozo de código con nombre que puedes usar todas las veces que quieras. Escribes la lógica una vez y la reutilizas (DRY: Don't Repeat Yourself, no te repitas).

Lo esencial

  • Una función es una receta: se declara una vez y no hace nada hasta que la llamas.
  • Los parámetros son los ingredientes: function sumar(a, b) → sumar(2, 3).
  • return devuelve el resultado para usarlo fuera; console.log solo lo enseña.
  • Cuando llega a un return, la función se acaba. En los bucles, el return va después del for.
  • Lo creado dentro de una función solo existe dentro (ámbito).

Las dos partes: declarar y llamar

// 1. DECLARACIÓN: las reglas del juego (aún no se ejecuta)
function sumar() {
  let suma = 12 + 4
  console.log(suma)
}

// 2. LLAMADA: aquí sí se ejecuta
sumar()   // 16
sumar()   // 16 otra vez

Sin los paréntesis () no se ejecuta. Escribir sumar solo nombra la función.

Diagrama: qué pasa al llamar a una función

1. La llamada manda los valores (2 y 3) a los parámetros (a y b). 2. La función hace su trabajo y con return devuelve el resultado al sitio desde donde la llamaste, que se guarda en r.

console.log dentro de la función solo enseña el valor; no lo devuelve. Para usar el resultado fuera, hace falta return.

Parámetros y return

function sumar(numero1, numero2) {  // parámetros: los "huecos"
  return numero1 + numero2          // devuelve el resultado
}

let resultado = sumar(2, 3)        // argumentos: lo que metes en los huecos
console.log(resultado)             // 5
  • Parámetros: datos que la función necesita para trabajar.
  • return: devuelve un valor para guardarlo en una variable. Después del return la función termina.
  • console.log solo enseña el valor por pantalla; return te lo da para seguir usándolo.

Parámetros por defecto (opcionales)

function nombreCompleto(name, surname = "Lopez") {
  console.log(`${name} ${surname}`)
}
nombreCompleto('Juan')           // Juan Lopez
nombreCompleto('Juan', 'Perez')  // Juan Perez

Si no le pasas ese dato, usa el valor por defecto.

Orden obligatorio: primero los parámetros obligatorios y al final los opcionales.

  • Local / de bloque: declarada dentro de una función o de unas llaves { } con let/const. Solo existe ahí y desaparece al terminar.
  • Por eso varias funciones pueden tener su propia variable resultado sin chocar.

Los 3 tipos de funciones

// 1. Declarativa
function multiplicar(a, b) {
  return a * b
}

// 2. Expresiva o anónima (sin nombre, guardada en una const)
const multiplicar2 = function (a, b) {
  return a * b
}

// 3. Flecha (arrow function)
const multiplicar3 = (a, b) => a * b
  • Declarativa: tiene hoisting, puedes llamarla incluso en una línea anterior a donde la escribiste.
  • Expresiva y flecha: sin hoisting, hay que declararlas antes de usarlas.
  • Las tres se llaman igual: multiplicar(2, 4) → 8.

Receta: convertir a función flecha

  1. Quita la palabra function y pon => después de los paréntesis.
  2. Si tiene un solo parámetro (ni 0 ni 2), puedes quitar los paréntesis.
  3. Si dentro de las llaves hay una sola línea, puedes quitar las llaves. Si esa línea tiene return, tienes que quitarlo (se devuelve solo).
// antes
const doble = function (n) { return n * 2 }
// paso 1
const doble = (n) => { return n * 2 }
// paso 2 y 3
const doble = n => n * 2

// con ternario, del profe:
const restar = (a, b) => (a >= b) ? a - b : b - a

Parámetros indefinidos (rest ...)

function sumar(...numeros) {   // numeros es un array

  for (let i = 0; i < numeros.length; i++) {
    suma = suma + numeros[i]      // o: suma += numeros[i]
  }

    if (numberOne > numberTwo) {
        return numberOne
    } else {
        return numberTwo
    }

    }

"Lo más grande hasta ahora" (el bibliotecario)

Para encontrar el libro más gordo entre millones, no los comparas todos con todos: te quedas en la mano con el más gordo hasta ahora y lo cambias solo si llega uno más gordo.

function findLongestWord(words) {

    for (let word of words) {
        if (word.length > longestWord.length) {
            longestWord = word        // cambio el que tengo en la mano
        }
    }
    return longestWord
}
  • length también vale para textos: cuenta las letras.
  • Con >, si hay un empate se queda el primero. Con >=, el último.

  • Funciones que llaman a funciones que llaman a funciones: es el día a día de programar.
  • Una variable no puede llamarse igual que una función (daba error con average; Héctor la llamó avg).

Intercambiar dos posiciones (swap)

function swap(array, i1, i2) {
    const guardado = array[i1]     // 1. me guardo el primero
    array[i1] = array[i2]          // 2. lo piso con el segundo
    array[i2] = guardado           // 3. pongo el guardado en el hueco
    return array
}

// ['Cristiano', 'Mesirve', 'Muralla']

  • Regla: si vas a cambiar un valor que todavía necesitas, guárdalo antes en una variable.
  • Es como cambiar el agua de dos vasos: hace falta un tercer vaso.

Arrays (listas)

Un array es una lista ordenada de valores guardada en una sola variable.

Lo esencial

  • Las posiciones empiezan en 0. length cuenta desde 1: la última está en length - 1.
  • Una posición que no existe da undefined.
  • lista.push(x) añade al final (funciona aunque sea const).
  • Los [ ] solo en arrays: precios[2]. Una variable normal va sin ellos.
  • Con [ ] a un texto sacas una letra: "Marta"[0] → "M".

Crear y leer

const frutas = ['Pera', 'Manzana', 'Platano', 'Ciruela']

frutas.length              // 4 (cuántos hay)
frutas[frutas.length - 1]  // 'Ciruela' (el último)

  • El último está en length - 1.
  • Se declaran con const: la variable siempre será ese array, pero puedes cambiar lo que hay dentro.
  • Un texto funciona parecido: 'Marta'[0] → 'M'.

1 · Qué es una base de datos

¿Para qué sirve una base de datos?

  • Persistencia: los datos sobreviven a recargas, apagones y reinicios.
  • Integridad: reglas que impiden datos sin sentido (edades negativas, pedidos sin cliente).
  • Seguridad: usuarios y permisos; cada uno ve y toca solo lo suyo.
  • Concurrencia: miles de usuarios leyendo y escribiendo a la vez sin pisarse.
  • Consultas rápidas: encontrar un registro entre millones en milisegundos.
  • Copias y recuperación: backups y transacciones: o se guarda todo, o no se guarda nada.

SELECT: pedir datos

SELECT columna1, columna2 FROM nombre_tabla;
SELECT * FROM nombre_tabla;     -- * = todas las columnas

  • Las sentencias acaban en ;. Con una sola consulta algunas herramientas no lo exigen, pero en cuanto hay varias seguidas es obligatorio: mejor ponerlo siempre.
  • Las palabras de SQL se escriben en MAYÚSCULAS por costumbre, para distinguirlas de los nombres de tablas y columnas.

AND, OR, NOT, IN, BETWEEN

IN es un atajo de varios OR seguidos. BETWEEN incluye los dos extremos: es lo mismo que velocidad >= 100 AND velocidad <= 120.

Son los mismos que en JS: AND = &&, OR = ||, NOT = !.

-- Paréntesis para mezclar AND y OR
WHERE (tipo = 'Fuego' OR tipo = 'Agua') AND ataque > 80

Ojo con mezclar: AND va antes que OR (como multiplicar antes que sumar). Sin paréntesis, lo de arriba significaría "los de Fuego (con cualquier ataque) o los de Agua con ataque > 80". Si mezclas, pon paréntesis siempre.

WHERE pais IS NULL          -- la casilla está vacía
WHERE pais IS NOT NULL      -- la casilla tiene algo

Ojo: para preguntar si algo está vacío se usa siempre IS NULL, nunca = NULL (con = no te sale nada).

LIKE: buscar por partes del texto

  • % = cualquier cantidad de letras (incluso ninguna).
  • _ = exactamente una letra.
WHERE nombre LIKE 'Char%'    -- empieza por "Char"
WHERE nombre LIKE '%chu%'    -- contiene "chu"
WHERE nombre LIKE '%ite'     -- termina en "ite"
WHERE nombre LIKE '_e%'      -- la 2ª letra es "e"

Es como el ejercicio de buscar nombres por letra de clase, pero sin bucle: lo hace la base de datos.

ORDER BY, LIMIT y DISTINCT

SELECT * FROM pokemon ORDER BY ataque DESC;   -- de mayor a menor
SELECT * FROM pokemon ORDER BY nombre;        -- ASC (de menor a mayor) por defecto
SELECT * FROM pokemon ORDER BY tipo, ataque DESC;  -- por tipo y, dentro de cada tipo, por ataque
SELECT * FROM pokemon LIMIT 5;                -- solo las 5 primeras filas
SELECT DISTINCT tipo FROM pokemon;            -- cada tipo una sola vez

Top 3: ORDER BY ataque DESC LIMIT 3 = los 3 con más ataque.

GROUP BY y HAVING

SELECT generacion, COUNT(*) AS total
FROM pokemon
GROUP BY generacion
HAVING total > 5;
  • GROUP BY junta las filas que tienen el mismo valor (por ejemplo, misma generación) y aplica la función a cada grupo.
  • WHERE filtra filas, antes de agrupar.
  • HAVING filtra grupos, después de agrupar.
  • La columna del GROUP BY va también en el SELECT, si no, no sabes de qué grupo es cada número.
  • Constrúyelo por pasos: primero el COUNT(*) solo, luego añades el GROUP BY, luego el HAVING y al final el ORDER BY. Si falla, sabes qué paso lo ha roto.

Matiz: usar el alias en HAVING total > 5 funciona en MySQL. En otras bases de datos hay que repetir la función: HAVING COUNT(*) > 5.

Orden de las partes de una consulta

Se escriben siempre en este orden (las que no uses, te las saltas):

SELECT→FROM→JOIN→WHERE→GROUP BY→HAVING→ORDER BY→LIMIT
SELECT tipo, AVG(ataque) AS media
FROM pokemon
WHERE generacion = 1
GROUP BY tipo
HAVING media > 70
ORDER BY media DESC
LIMIT 3;

En castellano: de los pokémon de la 1ª generación, agrúpalos por tipo, quédate con los tipos cuya media de ataque pase de 70 y enséñame los 3 mejores.

Para acordarte: Si Fulano Juega Wii, Gana Hasta Ocho Ligas (SELECT, FROM, JOIN, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT).

Diagrama: en qué orden lo procesa la base de datos

Se escribe empezando por SELECT, pero la base de datos lo ejecuta en este otro orden: primero coge la tabla, filtra, agrupa… y elige las columnas casi al final.

Por eso WHERE no puede usar COUNT(*): cuando se ejecuta WHERE, los grupos todavía no existen. Para filtrar por un recuento se usa HAVING.

3 · Varias tablas y subconsultas

JOIN: juntar varias tablas

Se une por la columna que conecta las tablas: la FK de una con la PK de la otra. En la base de series:

series.plataforma_id → plataformas.idvaloraciones.usuario_id → usuarios.idvaloraciones.serie_id → series.id
-- Dos tablas: título + nombre de la plataforma
SELECT s.titulo, p.nombre
FROM series s
JOIN plataformas p ON s.plataforma_id = p.id;

-- Tres tablas: lo que ha valorado Lucía (valoraciones hace de puente)
SELECT s.titulo, v.puntuacion
FROM valoraciones v
JOIN usuarios u ON v.usuario_id = u.id
JOIN series   s ON v.serie_id   = s.id
WHERE u.nombre = 'Lucía';

-- «Lo que no tiene pareja»: plataformas sin series
SELECT p.nombre
FROM plataformas p
LEFT JOIN series s ON s.plataforma_id = p.id
WHERE s.id IS NULL;
  • s, p, u, v son apodos de las tablas, para no escribir el nombre entero. s.titulo = la columna titulo de la tabla series.
  • El ON dice por dónde se cosen las dos tablas: casi siempre FK = PK.

4 · Crear y modificar

Subconsultas, NOT IN y COUNT(DISTINCT)

Una subconsulta es un SELECT dentro de otro, entre paréntesis. Se ejecuta primero y su resultado lo usa la consulta de fuera.

-- Devuelve UN valor: pokémon con más ataque que la media
SELECT nombre, ataque
FROM pokemon
WHERE ataque > (SELECT AVG(ataque) FROM pokemon);

-- Devuelve UNA LISTA: plataformas que no tienen ninguna serie
SELECT nombre
FROM plataformas
WHERE id NOT IN (SELECT plataforma_id FROM series);

-- Contar sin repetir: cuántos usuarios distintos han valorado
SELECT COUNT(DISTINCT usuario_id) AS usuarios
FROM valoraciones;
  • Así la media la calcula la consulta: si cambian los datos, se recalcula sola. No escribas el número a mano.
  • NOT IN = "que no esté en esta lista". Lo mismo se hace con LEFT JOIN … WHERE … IS NULL.
  • COUNT(DISTINCT col) cuenta valores distintos. Tras un JOIN, COUNT(*) cuenta filas, y un mismo pedido o usuario puede salir varias veces.

Ojo con NOT IN: si la subconsulta devuelve algún NULL, no sale nada. Con LEFT JOIN … IS NULL no pasa.

Subconsulta correlacionada y fechas

-- Pokémon con más ataque que la media DE SU generación
SELECT p.nombre, p.ataque, p.generacion
FROM pokemon p
WHERE p.ataque > (SELECT AVG(p2.ataque)
                  FROM pokemon p2
                  WHERE p2.generacion = p.generacion);

-- Agrupar por mes: DATE_FORMAT convierte la fecha en '2026-01'
SELECT DATE_FORMAT(fecha, '%Y-%m') AS mes, COUNT(*) AS total
FROM pedidos
GROUP BY mes
ORDER BY mes;
  • Correlacionada: la subconsulta usa una columna de la de fuera (p.generacion), así que se calcula otra vez para cada fila. Hacen falta dos alias de la misma tabla (p y p2).
  • DATE_FORMAT(fecha, formato): %Y año, %m mes, %d día.

Crear la base de datos y las tablas

Crear y cambiar la estructura se llama DDL (CREATE, ALTER, DROP). Meter y cambiar datos es DML (INSERT, UPDATE, DELETE) y consultar es DQL (SELECT).

CREATE DATABASE seriesdb;   -- crea la base de datos
USE seriesdb;               -- trabaja dentro de ella

CREATE TABLE plataformas (
  id             INT AUTO_INCREMENT PRIMARY KEY,
  nombre         VARCHAR(50) NOT NULL UNIQUE,
  precio_mensual DECIMAL(5,2)
);

CREATE TABLE series (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  titulo        VARCHAR(100) NOT NULL,
  plataforma_id INT NOT NULL,
  nota          DECIMAL(3,1),
  finalizada    BOOLEAN DEFAULT FALSE,
  FOREIGN KEY (plataforma_id) REFERENCES plataformas(id)
);

Primero se crea la tabla a la que se apunta (plataformas) y luego la que tiene la FK (series). Al revés da error porque la FK apuntaría a algo que no existe.

Meter, cambiar y borrar datos

-- Añadir filas (sin el id: lo pone AUTO_INCREMENT)

Node.js y API REST

Clases 10 a 15 con Juan. Node es el backend que une lo de SQL con lo de JavaScript: recibe una petición, busca los datos y los devuelve en JSON. Ordenado por temas, de lo más general a lo más práctico.

Lo esencial

  • Node = JavaScript fuera del navegador. Una API REST devuelve datos en JSON, no páginas.
  • CRUD: GET leer · POST crear · PUT actualizar · DELETE borrar. Siempre se responde algo.
  • Pedir datos tarda: es asíncrono. Una promesa acaba en resolve o reject; se usa con await dentro de async y try / catch.
  • Proyecto: npm init con "type": "module", librerías con npm install, archivos conectados con export / import (con .js).
  • Express: app.verbo('/ruta', (req, res) => { … }) + app.listen(3000). Se arranca con npm run dev y se para con Ctrl + C.
  • Datos por la URL → req.params (siempre texto). Datos por el cuerpo → req.body (necesita app.use(express.json())).
  • Buscar uno → find (o undefined). Buscar varios → filter (o []).
  • Proyecto real: index.js → app.js → routes → middlewares → controllers → models → MySQL. Las contraseñas van en .env, que nunca se sube a GitHub, y se leen con process.env.NOMBRE.
  • El controlador responde (res.json); el modelo consulta MySQL (await db.execute(…)). Los dos son async.
  • Valores en la consulta con ? y un array (execute('… where id = ?', [id])), nunca con ${}: evita la inyección SQL.
  • const [result] siempre; luego return result si quieres muchas filas y return result[0] si quieres una. En delete y update se mira affectedRows; en insert, insertId.

1 · Qué es una API REST

Por qué existe una API REST

  • Antes: el backend (PHP, Java…) pedía los datos y él mismo montaba el HTML de la página.
  • Con los móviles, la misma tienda necesitaba web y apps (iOS, Android) con la misma base de datos. Un equipo para cada cosa: carísimo.
  • 2010, Node.js: JavaScript sale del navegador y puede funcionar en un servidor.
  • La solución: un "traductor" en medio. El backend ya no devuelve HTML, devuelve datos en JSON, y los entiende cualquiera: la web en React, la app, una Smart TV…

Ejemplo: la web de la Dragon Ball API enseña a Goku con su foto. En su dirección /api/characters ves los mismos datos en crudo, en JSON. Eso es lo que hace Node: los datos, sin dibujo.

2 · Asincronía y promesas

Síncrono y asíncrono

  • Síncrono: JS va línea a línea; hasta que no acaba una, no empieza la siguiente.
  • El problema: pedir algo a una base de datos o a internet tarda. Si todo esperase en fila, la web se congelaría.
  • Asíncrono: JS encarga la tarea lenta, sigue con lo demás y la recoge cuando llega.
setTimeout(() => {
    console.log('Hola')
}, 3000)              // espera 3 segundos

console.log('Adiós')

// Sale primero "Adiós" y a los 3 segundos "Hola"

A veces sí hay que esperar: si la línea siguiente usa los datos que pediste, necesitas que lleguen antes. Para eso están las promesas.

Promesas: resolve, reject, await y try/catch

Una promesa es una tarea que acabará más tarde, bien o mal.

function pedirNota(nota) {
    return new Promise((resolve, reject) => {
        if (nota >= 0 && nota < 5) {
            resolve('Suspenso')          // resultado esperado
        } else if (nota >= 5 && nota <= 10) {
            resolve('Aprobado')          // resultado esperado
        } else {
            reject('Nota no válida')     // algo inesperado: 'Pepe', 100…
        }
    })
}

async function mostrar() {
    try {
        const resultado = await pedirNota(7)   // espera a que acabe
        console.log(resultado)                 // Aprobado
    } catch (error) {
        console.log(error)                     // Nota no válida
    }
}

new Promise((resolve, reject) => { … })crea la promesa; la estructura es siempre esta

await"espera a que acabe" antes de seguir; solo dentro de async
try { } catch { }lo del resolve sigue en el try; lo del reject salta al catch
.then(…).catch(…)la otra forma de usarlas: .then recibe el resolve y .catch el reject

¿Resolve o reject? Un suspenso o un array vacío no son errores: son resultados esperados (resolve). Es reject cuando algo falla de verdad: un error de SQL o un dato sin sentido. Lo importante ahora es saber usarlas con await, porque las consultas a la base de datos devuelven promesas.

Rutas estáticas y dinámicas

Cuándo dos rutas son la misma

  • Un parámetro con : es una cajita que admite cualquier cosa. /pais/:nombre y /pais/:id son la misma ruta.
  • Con el mismo verbo, Express usa la primera que esté escrita; la otra nunca se ejecuta.
  • Ruta = verbo + dirección. GET /pais/:pais y DELETE /pais/:id conviven sin problema.
  • Por eso se pone una parte fija delante: /pais/id/:id ya no choca con /pais/:nombre.

    } else {

})

    const nuevoPais = req.body
    arrayPaises.push(nuevoPais)
    res.json(arrayPaises)
})

// PUT: actualizar un país (id por URL + datos por body)
app.put('/update/pais/:id', (req, res) => {
    const data = req.body
    const id = Number(req.params.id)
    const dataPais = arrayPaises.find(pais => pais.id === id)
    dataPais.capital = data.capital
    res.json(dataPais)
})

// DELETE: borrar un país (id por URL)
app.delete('/pais/:id', (req, res) => {
    const id = Number(req.params.id)
    const resultado = arrayPaises.filter(pais => pais.id !== id)
    res.json(resultado)
})

No hay persistencia: lo que crees o cambies vive en memoria; al reiniciar el servidor, el array vuelve a ser el de data.js. Guardar de verdad es cosa de la base de datos.

GET: buscar y responder siempre

  • Si find no encuentra nada devuelve undefined, y undefined.capital rompe el servidor. Por eso el if: es el "no hay resultados" de cualquier buscador.
  • if (data !== undefined) y if (data) hacen lo mismo: undefined cuenta como falso.
  • Compara país con país (item.pais), no con la capital.
  • En MySQL no hace falta toLowerCase: por defecto no distingue mayúsculas.

Tildes y ñ: la función sanitize

export function sanitize(palabra) {
    let resultado = palabra.toLowerCase()       // 'Irán' → 'irán'
    resultado = resultado.replaceAll('á', 'a')  // 'irán' → 'iran'
    resultado = resultado.replaceAll('é', 'e')
    resultado = resultado.replaceAll('í', 'i')
    resultado = resultado.replaceAll('ó', 'o')
    resultado = resultado.replaceAll('ú', 'u')
    resultado = resultado.replaceAll('ñ', 'n')
    return resultado
}
  • Se limpian los dos lados antes de comparar: lo que llega y lo del array. El array no cambia: solo se compara una copia limpia.
  • En nombres de archivos, carpetas y rutas, mejor sin espacios, tildes ni ñ: en una URL se codifican (un espacio es %20). Usa _ o -.

POST: crear con el body

  • Para mandar un objeto entero se usa el cuerpo de la petición: req.body. Necesita app.use(express.json()) justo después de const app = express(); sin eso, req.body es undefined.
  • En el cliente: verbo POST y pestaña Body → JSON.
  • Así conectan front y back: en React capturarás un formulario, montarás este objeto y lo mandarás por POST.
{ "id": 5, "pais": "Finlandia", "capital": "Helsinki" }

JSON estricto (el del body): claves y textos con comillas dobles, y sin coma después del último dato. El id va a mano; en MySQL se pone solo (autoincremental).

PUT: actualizar (params + body)

  1. Buscar el país por id con find (el id pasado a número).
  2. Cambiar la propiedad: dataPais.capital = data.capital.
  3. Responder con el país actualizado: res.json(dataPais).

Ojo: si el id no existe, dataPais es undefined y el servidor da error 500. Habría que comprobar if (dataPais) antes de cambiarlo.

DELETE: borrar por id

  • Truco típico: borrar = quedarte con todos menos ese, con filter(pais => pais.id !== id).
  • Otros métodos: pop() borra el último, shift() el primero y splice(posición, 1) uno en una posición (pero necesitas la posición, no el id).

Ojo: filter crea un array nuevo: arrayPaises sigue igual y un GET posterior todavía encuentra el país. Con base de datos se hará un DELETE y luego un SELECT.

Borrado físico y lógico: el físico es el DELETE. El lógico es un campo tipo activo a 0 o 1: el usuario desaparece, pero los datos se quedan (las tiendas, por ley, guardan las compras unos años).

El servidor: index.js + src/app.js

Lo que antes estaba en un solo archivo se parte en dos: app.js configura Express, e index.js crea el servidor HTTP y lo arranca. Esta parte casi nunca cambia de un proyecto a otro.

// src/app.js: solo configura Express
import express from 'express'

export const app = express()
app.use(express.json())        // para leer req.body

// index.js: crea y arranca el servidor
import http from 'node:http'
import { app } from './src/app.js'

const server = http.createServer(app)
const PORT = 3000
server.listen(PORT)

server.on('listening', () => {     // si arranca bien
    console.log(`Servidor funcionando en el puerto ${PORT}`)
})

server.on('error', (error) => {    // si falla al arrancar
    console.log(error)
})
  • node:http viene con Node, no hay que instalarlo. http.createServer(app) crea un servidor que usa la app de Express.
  • server.on('evento', función) ejecuta la función cuando pasa ese evento.
  • Las variables se escriben siempre igual: si es PORT, en mayúsculas en todos los sitios.

Ojo, dos fallos del código de clase: los eventos se llaman 'listening' y 'error', en inglés y en minúscula. Con 'Escuchando' o 'Error' nunca se ejecutan. Y si app.js exporta con export const app, se importa con llaves (import { app }). Sin llaves solo vale si exportas con export default app.

app.js: la configuración del servidor

import express from 'express'
import cors from 'cors'
import apiRoutes from './routes/api.routes.js'

const app = express()
app.use(express.json())        // leer req.body
app.use(cors())                // con paréntesis: si no, todo se queda colgado

app.use('/api', apiRoutes)     // todo lo que empiece por /api va a las rutas

// 404: ninguna ruta ha respondido
app.use((req, res, next) => {
    res.status(404).json({ message: 'Not found' })
})

// 500: ha habido un error en algún sitio
app.use((err, req, res, next) => {
    console.log(err.stack)                         // el detalle, para ti, en la terminal
    res.status(500).json({ message: err.message }) // un mensaje, para quien usa la API
})

export default app
  • CORS: los navegadores no dejan que dos aplicaciones (por ejemplo tu React y tu API) se hablen si no se autoriza. cors() dice "esta conexión es legítima".
  • /api: separa la web de los datos. midominio.com/users podría ser una página, y midominio.com/api/users, los datos en JSON.
  • Middleware y next: una función que se pone delante, como el portero de una discoteca. Si todo va bien, llama a next() y te deja pasar a la siguiente; si no, responde él.
  • El orden importa: el 404 va después de las rutas, porque solo debe saltar si ninguna ha respondido. El de errores es el que tiene cuatro parámetros (err primero).
  • Códigos de estado: 200 todo bien, 404 no existe, 500 error del servidor. Una API siempre responde JSON, también cuando falla.

Controlador, modelo y conexión: el flujo de "todas las mascotas"

// config/db.js: la conexión
import { createPool } from 'mysql2/promise'

const pool = createPool({
    user: process.env.DB_USER,

// models/mascotas.model.js: la consulta
import db from '../config/db.js'

const selectAll = async () => {
    const [result] = await db.execute('SELECT * FROM mascota')
    return result
}

export { selectAll }
// controllers/mascotas.controller.js: la respuesta
import { selectAll } from '../models/mascotas.model.js'

const getAll = async (req, res) => {
    const mascotas = await selectAll()
    res.json(mascotas)
}
  • mysql2/promise: la versión de mysql2 que trabaja con promesas (asíncrona). createPool crea un "pool" (piscina) de conexiones con MySQL.
  • Las consultas tardan, así que devuelven promesas: el modelo y el controlador son funciones async y usan await. Es la diferencia con el array de países.
  • db.execute('…') lanza la consulta SQL, escrita tal cual entre comillas.
  • El return del modelo vuelve al controlador, y el res.json del controlador vuelve por las rutas y la app hasta quien pidió los datos.

Ojo con los corchetes: execute devuelve dos cosas: las filas y la información de las columnas. Con const [result] = … (corchetes a la izquierda) te quedas solo con las filas. En clase se escribió return [result], que hace lo contrario: mete todo en otro array más y las mascotas salen anidadas junto a datos técnicos.

export default o export { }

  • export default algo: lo principal del archivo, y solo puede haber uno. Se importa sin llaves y con el nombre que tú quieras: import apiRoutes from './routes/api.routes.js', aunque dentro se llame router.
  • export { a, b, c }: varias cosas con nombre. Se importan con llaves y con el mismo nombre: import { selectAll } from ….
  • Regla práctica: si el archivo tiene una sola cosa que exportar (app, router, pool), default. Si tiene varias funciones (controladores, modelos), la lista al final.
  • La lista va al final del archivo: export { getAll, getById, … }. Tiene que haber tantos nombres como funciones, y escritos igual.

Cómo encontrar dónde se atasca

  • Si una petición se queda cargando, pon un console.log('app'), console.log('rutas'), console.log('controlador')… al principio de cada archivo o función.
  • Mira en la terminal hasta dónde llega: el fallo está en el siguiente paso, el que ya no aparece.
  • Juan lo encontró así en clase: llegaba al controlador, pero se quedaba atascado justo después.

9 · El CRUD completo de la veterinaria

La receta: siempre es igual

Una vez montados index.js, app.js y api.routes.js, no se vuelven a tocar. A partir de ahí, cada endpoint es repetir lo mismo: ruta → controlador → modelo.

  1. Ruta (entidad.routes.js): verbo + ruta + nombre de la función del controlador.
  2. Controlador (entidad.controller.js): una función con el mismo nombre que en la ruta. Recoge lo que llega (req.params o req.body), llama al modelo con await y responde con res.json(…).
  3. Modelo (entidad.model.js): una función con otro nombre (suele llevar el de la consulta: selectById, deletePetById…). Hace await db.execute(…) y devuelve el resultado con return.
ArchivoImportaExporta
rutaslas funciones del controladorsolo el router (export default)
controladorlas funciones del modelotodas sus funciones (export { … })
modelosolo la conexión (db)todas sus funciones (export { … })
  • Si una función sale oscurita en VS Code, es que nadie la usa: casi siempre falta el export o el import.
  • El controlador y el modelo no pueden llamarse igual: en el controlador estarías importando y creando una función con el mismo nombre en el mismo archivo.
  • En archivos distintos, en cambio, sí se puede repetir nombre: cada archivo de rutas tiene su const router y cada controlador puede tener su getAll. Son como dos personas que se llaman igual en ciudades distintas: no se confunden.
  • Para saber qué parámetro recibe una función del modelo, mira con qué la llamas en el controlador. Para saber qué llega por req.params, mira qué lleva dos puntos en la ruta.

Leer: una mascota, su especie y todas las de una especie

// rutas
router.get('/:idMascota', getById)                   // /api/mascotas/2
router.get('/:idMascota/especie', getBySpecies)      // /api/mascotas/2/especie
router.get('/especie/all/:especie', getAllBySpecies) // /api/mascotas/especie/all/perro
// controlador
const getById = async (req, res) => {
    const unaMascota = await selectById(Number(req.params.idMascota))
    res.json(unaMascota)
}

const getBySpecies = async (req, res) => {
    const especie = await selectSpeciesById(Number(req.params.idMascota))
    res.json(especie)                      // { "especie": "gato" }
}

const getAllBySpecies = async (req, res) => {
    const lista = await selectAllBySpecies(req.params.especie)   // sin Number: es texto
    res.json(lista)
}
// modelo
const selectById = async (idMascota) => {
    const [result] = await db.execute('select * from mascota where id = ?', [idMascota])
    return result[0]                       // una sola mascota
}

const selectSpeciesById = async (idMascota) => {
    const [result] = await db.execute('select especie from mascota where id = ?', [idMascota])
    return result[0]
}

const selectAllBySpecies = async (especie) => {
    const [result] = await db.execute('select * from mascota where especie = ?', [especie])
    return result                          // todas: el array entero
}
  • Lo que llega por la ruta siempre es texto. Los id en MySQL son siempre números enteros (en MongoDB serán textos), así que el id se pasa por Number().
  • La especie no: "perro" es texto y en la base de datos también. Hay cosas mecánicas y cosas que hay que pensar.
  • Una ruta puede tener varios parámetros: '/:idMascota/:especie' se lee con req.params.idMascota y req.params.especie. El nombre lo eliges tú en la ruta.

Las interrogaciones ?

  • La consulta es un texto. Con comillas invertidas podrías meter la variable: `… where id = ${idMascota}`. No se hace así: si alguien mete un trozo de SQL en la URL, se ejecutaría dentro de tu consulta. Eso es la inyección SQL.
  • Lo correcto: un ? en cada hueco y, después de la coma, un array con los valores: execute('… where id = ?', [idMascota]). execute los mete como datos, no como SQL.
  • Tantos ? como valores, y en el mismo orden. Si hay 2 interrogaciones, el array lleva 2 valores.

Los corchetes, paso a paso

  • La base de datos siempre devuelve un array, aunque busques una sola fila. Y execute lo mete dentro de otro array junto con información técnica.
  • const [result] = … quita el array de fuera: te quedas con las filas.
  • ¿Quieres muchas (todas, todas las de una especie)? return result.
  • ¿Quieres una (por id)? return result[0]: el primer y único elemento.
  • Si no sabes qué devuelve, haz return result (o console.log(result)), mira la respuesta y luego decide. No hace falta aprenderlo de memoria.

Borrar: affectedRows y tu propia respuesta

// controlador
const deletePet = async (req, res) => {
    const respuesta = await deletePetById(Number(req.params.idMascota))
    res.json(respuesta)
}

// modelo
const deletePetById = async (idMascota) => {
    const [result] = await db.execute('delete from mascota where id = ?', [idMascota])
    if (result.affectedRows === 1) {
        return { status: true, message: 'La mascota se ha borrado correctamente' }
    } else {
        return { status: false, message: 'Ha ocurrido un error, inténtalo de nuevo' }
    }
}
  • Un delete no devuelve filas: devuelve un objeto con datos técnicos. Lo único útil es affectedRows, cuántas filas ha cambiado.
  • Borrando por id solo puede ser 1 (se borró) o 0 (no existía: si borras dos veces la misma, la segunda da 0).
  • Cuando la base de datos no responde nada que le sirva al usuario, creas tu propio JSON con un status y un message. Es el típico "Ha ocurrido un error" de las webs.

Crear: req.body e insertId

// controlador
const insertPet = async (req, res) => {
    const idNuevaMascota = await insertNewPet(req.body)   // la BD solo devuelve el id
    const mascota = await selectById(idNuevaMascota)      // con el id, la busco entera
    res.json(mascota)
}

// modelo (resumido: en el proyecto van los 13 campos)
const insertNewPet = async ({ id_dueno, nombre, especie, raza = null, color = null }) => {
    const [result] = await db.execute(
        'insert into mascota (id_dueno, nombre, especie, raza, color) values (?, ?, ?, ?, ?)',
        [id_dueno, nombre, especie, raza, color]
    )
    return result.insertId
}
  • POST no tiene parámetros de ruta: los datos llegan en el body (un JSON). En el futuro vendrán de un formulario de React.
  • El modelo separa el objeto en variables con llaves: ({ id_dueno, nombre, … }). El = null pone un valor por defecto si ese dato no llega.
  • Un insert solo devuelve el id nuevo (result.insertId). Para devolver la mascota completa, se llama a selectById (la función del modelo, no el controlador getById, que espera req y res).
  • Si una columna es NOT NULL, ese dato hay que enviarlo siempre. Las que admiten nulo pueden faltar.

Truco para probarlo: haz un GET de todas, copia una mascota entera, pégala en el body del POST y bórrale el id (se pone solo, es autoincremental). Deja el id_dueno, que es el que la relaciona con su dueño.

Actualizar: req.params + req.body

// controlador

    const dataMascota = req.body                      // los datos nuevos

    if (respuesta.affectedRows === 1) {
        const mascota = await selectById(idMascota)

    } else {
        res.json({ status: false, message: 'No se ha podido actualizar la mascota' })
    }
}

// modelo (resumido)

    const [result] = await db.execute(
        'update mascota set id_dueno = ?, nombre = ?, especie = ? where id = ?',
        [id_dueno, nombre, especie, idMascota]        // el id va el último, por el where
    )
    return result
}
  • Es el que más cosas tiene: el id por la URL y los datos por el body. El objeto del body es el mismo que en el POST.
  • Igual que en el borrado, se mira affectedRows: si es 1, se busca la mascota y se devuelve entera.

HTML y CSS

Clases 16 a 19, con Héctor. HTML da la estructura de la página (qué hay) y CSS el aspecto (cómo se ve). Primero se aprende que las cosas existen; luego, cuando hacen falta, se buscan.

Lo esencial

  • HTML no es un lenguaje de programación: es un lenguaje de marcas. Todo va envuelto en etiquetas, y es estático (no hace cosas por sí solo).
  • Casi todas las etiquetas se abren y se cierran: <p>…</p>. Algunas son autocontenidas y no se cierran: <br>, <img>, <input>.
  • Estructura: <html> → <head> (información de la página) + <body> (el contenido que se ve).
  • Los atributos dan información a una etiqueta: nombre="valor", con comillas dobles. Ej.: <img src="gatos.jpg">.
  • Rutas: relativas (desde el archivo: img/gato.jpg, ../img/gato.jpg) o absolutas (desde la raíz del proyecto: /img/gato.jpg).
  • Formularios: cada campo es un <input> con type, id y name, y su <label for="id">.
  • CSS se carga de 3 formas; la buena es un archivo aparte: <link rel="stylesheet" href="styles.css">.
  • Ábrelo siempre con Live Server, no con doble clic.
  • Selectores: p (etiqueta), .clase, #id, .padre p (dentro de). Si dos reglas chocan, gana la más específica.
  • Toda caja tiene contenido → padding → border → margin. Con * { box-sizing: border-box; } mide lo que dices.
  • Flexbox va en el padre: display: flex + justify-content (dirección del flex) + align-items (el otro eje) + flex-wrap: wrap.
  • position: absolute (respecto a la página) o fixed (pegado a la pantalla) + z-index para las capas.
  • F12 es tu amigo: ves las cajas y las reglas tachadas.
  • :hover (ratón encima) + transition en el elemento = cambios suaves. @keyframes + animation = movimiento solo. ::before/::after con content añaden contenido.
  • Responsive = que se vea bien en todos los tamaños. Se escribe primero el móvil y luego @media screen and (min-width: 768px) { … } cambia solo lo necesario en pantallas más grandes.
  • calc(100% - 300px) = "lo que sobre".

La estructura de una página

<!DOCTYPE html>
<html lang="es">
<head>
    <meta charset="UTF-8">                 <!-- tildes, eñes y emojis bien -->
    <title>Mi primerita página</title>   <!-- el texto de la pestaña -->
    <link rel="stylesheet" href="styles.css">

  • head = información sobre la página: título de la pestaña, idioma, qué CSS carga, el charset… No se ve en la página.
  • body = el contenido que se ve.
  • No confundas head (la cabecera del documento) con header (la parte de arriba de la web, que va dentro del body).
  • Casi todo es opcional: el navegador intenta adivinar lo que quieres y pinta algo igualmente. Pero la estructura completa es la forma limpia.

Atajos de VS Code (Emmet): ! + Tab escribe toda la estructura. lorem + Tab escribe texto de relleno (lorem20 = 20 palabras). Si Tab no va, prueba Enter en la sugerencia o Ctrl + Espacio.

3 · Imágenes, atributos y rutas

La imagen y sus atributos

<img src="gatos.jpg" alt="Seis gatos" width="200" height="100">
  • img es autocontenida: todo va en atributos.
  • src (source): de dónde sale la imagen.
  • width (ancho) y height (alto) existen, pero no se recomiendan: deforman la imagen si no respetas la proporción, y para eso está CSS.
  • Puedes poner atributos inventados y el navegador los ignora, pero es mala práctica. Hay atributos reservados, como src, que sí hacen algo.

Imágenes de internet: src puede ser un enlace externo, pero si ese servidor la cambia o la borra, tu página se rompe. Lo normal es descargarla en tu proyecto, y en el trabajo usar bancos de imágenes sin copyright.

La etiqueta a

Campos de un formulario

    <label for="color-red">Rojo</label>

        <option value="jp">Japón</option>
    </select>

    <button type="submit">Enviar</button>

Así se ve en el navegador

Los atributos de un campo

  • type: qué tipo de campo es. Si no lo pones, es text.
  • id: para que el label lo encuentre. Pon nombres con sentido (age-input, no manzana).
  • name: el nombre con el que se envía el dato. En los radio y checkbox, el mismo name los agrupa.
  • <label for="id">: el texto del campo. Si haces clic en él, el campo coge el foco (como si hicieras clic en la caja).
  • value: el valor que ya viene escrito. En un radio o checkbox, lo que se envía.
  • placeholder: un texto de ejemplo en gris que desaparece al escribir. No es un valor.
  • checked: radio o checkbox marcado por defecto. multiple: permite elegir varios en un select (con Ctrl).

Tipos de input

texttexto libre
numbersolo números, con flechitas. Ojo: deja escribir la e (de 1e10)
dateun calendario para elegir fecha
radioelegir uno de varios
checkboxmarcar varios

Un button dentro de un formulario envía el formulario por defecto (type="submit"). Si no quieres que lo envíe: type="button".

Validar en el navegador no es seguridad

  • maxlength, min, max… son validación en cliente: ayudan al usuario (usabilidad, UX).
  • Pero cualquiera puede quitarlos con las herramientas del navegador (F12). Nada del navegador es seguro.
  • La validación de verdad se hace en el servidor (en la API de Node), antes de guardar en la base de datos.

A dónde va el formulario: GET o POST

  • action: la URL a la que se envía, por ejemplo una ruta de tu API que da de alta usuarios. Vacío = a la misma página.
  • method="get" (por defecto): los datos van en la URL, después de un ?: index.html?first-name=Paco&age=13. Es la query string. Útil para búsquedas y filtros (Google lo hace así).
  • method="post": los datos van por dentro, sin verse en la URL. Para contraseñas y datos privados. Se ven en F12 → Network → Form Data.

Es lo mismo que en la API de la veterinaria: el POST lleva los datos en el req.body.

7 · CSS: cómo cargar estilos

Las 3 formas de poner CSS

<!-- 1. inline: en el atributo style de una etiqueta -->
<h1 style="color: red">Rojo</h1>

<!-- 2. etiqueta <style> en el head -->
<style>
    h2 { color: green; }       /* todos los h2, verdes */
</style>

<!-- 3. archivo aparte (la recomendada), en el head -->
<link rel="stylesheet" href="styles.css">
/* styles.css */
h3 {
    color: blue;
}
Así se ve en el navegador
  • Un archivo CSS no hace nada solo por existir: hay que cargarlo en el HTML con <link>, igual que una imagen se carga con src.
  • rel="stylesheet" dice que es una hoja de estilos. Sin él, no se aplica.
  • href es la ruta al archivo, relativa o absoluta.
  • Los comentarios de CSS son como los de JS multilínea: /* … */.

Muchos atributos de HTML para dar estilo (width, height, border) existen porque HTML se inventó antes que CSS. Hoy el aspecto se pone siempre con CSS.

Cómo se escribe una regla de CSS

  • Si dos reglas dicen cosas distintas al mismo elemento, gana la más específica. Por ejemplo, footer p gana a p, y p.enorme gana a .enorme.
  • De menos a más: * → etiqueta (p) → clase (.enorme) → id (#algo) → style="…" en la etiqueta.
  • Si las dos son igual de específicas, gana la que está más abajo en el archivo. Es el único caso en que importa el orden.
  • Por legibilidad, lo general va arriba (*, body) y lo concreto, abajo.

!important y el "reset"

  • color: red !important; se salta la especificidad y gana siempre.
  • Úsalo lo mínimo: si tu CSS está lleno de !important, es que algo está mal planteado. Tiene sentido para pisar estilos de una plantilla comprada o que mete JavaScript.
  • Cada navegador pone sus estilos por defecto (en F12 salen como user agent stylesheet). Por ejemplo, márgenes en el body y en los párrafos.
  • Un archivo reset.css los quita para empezar de cero. Es de las cosas que tiene sentido pedirle a la IA, porque cambia con cada versión de los navegadores.

  • Unidades: px (píxeles, la que usaremos), % (respecto al padre, normalmente), vw/vh (% del ancho o alto de la pantalla), rem (respecto al tamaño de letra del navegador, para accesibilidad).

.amarilla {
    order: -1;            /* todos tienen 0: menor = antes, mayor = después */
    align-self: flex-end; /* como align-items, pero solo para este */
    flex-grow: 1;         /* cuánto crece si SOBRA espacio */
}
  • order funciona como el z-index: todos empiezan en 0. Con 1 va detrás de todos; con -1, delante de todos.
  • flex-grow solo se nota si sobra espacio en el contenedor. En la práctica, para que algo ocupe más se suele usar su width.
  • flex-shrink: lo contrario, cuánto se encoge si falta espacio.
Así se ve en el navegador

Para practicar: Flexbox Froggy (flexboxfroggy.com), el juego de las ranas de clase.

14 · Maquetar una página paso a paso (la tienda)

El método: poquito a poco

  • Haz una parte (la barra de arriba), compruébala en el navegador y solo entonces pasa a la siguiente (las tarjetas). No escribas todo y pruebes al final.
  • El CSS es prueba y error: pones algo, lo miras, lo cambias… hasta que queda como quieres.
  • Pon un background de color llamativo mientras maquetas para ver dónde está cada caja; luego lo quitas.
  • Da estilos con clases, no directamente a etiquetas (h1 { … }): si mañana añades otro h1 en otra parte, también le afectaría.

Codificación: qué es el UTF-8

  • El ordenador solo guarda ceros y unos. Una codificación es la tabla que dice qué combinación es cada letra: "esto es una A, esto una B…".

  • <meta charset="UTF-8"> le dice al navegador en qué "idioma" está escrito el archivo. Si no coinciden, salen las letras raras (Ã±, �) en tildes y eñes. Pasa también al abrir CSV en Excel.

15 · Pseudoclases y pseudoelementos

Pseudoclases: :hover, :visited, :focus, :active

Aplican un estilo solo cuando el elemento está en un estado. Se escriben con un solo : pegado al selector.

.menu a:hover   { color: yellow; text-decoration: underline; }   /* ratón encima */
a:visited       { color: red; }      /* enlaces ya visitados (por defecto, morados) */
a:focus         { color: green; }    /* tiene el foco: al hacer clic o al llegar con Tab */
a:active        { color: orange; }   /* mientras lo estás pulsando */
Pásale el ratón, haz clic o usa Tab

Ojo con el :hover en el móvil: en una pantalla táctil no hay ratón "encima", así que no existe. No escondas cosas importantes detrás de un hover.

Pseudoelementos: ::before y ::after

Añaden contenido antes o después del contenido de un elemento, desde el CSS. Se escriben con dos ::, y llevan content obligatoriamente: sin él, no aparece nada.

.poem::before {
    content: '<<';
}
.poem::after {
    content: '>>';
    color: pink;
    margin-left: 20px;
}
Así se ve en el navegador
  • Se usan para las comillas de una cita, iconitos, el "tic" de los interruptores… Las fuentes de iconos también funcionan así por dentro.
  • Al contenido añadido se le aplica cualquier estilo: color, margen, subrayado…

16 · Transiciones y transform

transition: que el cambio sea suave

.poem {
    background: #f5f5f5;
    padding: 10px;
    transition: all 0.5s;          /* la transición va en el ELEMENTO, no en el :hover */
}
.poem:hover {
    background: pink;
    padding: 20px;
}
Pasa el ratón por cada caja
  • Sin transition, el cambio es brusco, de golpe. Queda mal.
  • Va en el elemento normal (el que va a cambiar), no en la regla del :hover.
  • all = cualquier propiedad que cambie. También puedes poner solo una: transition: background 5s.
  • El tiempo, con medida: medio segundo suele quedar bien. 10 segundos es insufrible.
  • Se puede añadir el ritmo: ease, ease-in (empieza lento), ease-out (acaba lento), ease-in-out. Ejemplo: transition: all 0.5s ease-in-out.

transform: crecer, mover, girar

.tarjeta { transition: transform 0.3s; }
.tarjeta:hover {
    transform: scale(1.05);          /* un 5% más grande */
    /* transform: translateY(-10px);    sube 10px */
    /* transform: rotate(10deg);        gira 10 grados */
}
Pasa el ratón por cada tarjeta
  • Para que algo crezca al pasar el ratón, mejor scale que cambiar el padding o el width.
  • Ojo: transform es solo visual. La caja no ocupa más sitio, así que puede montarse encima de las de al lado.

17 · Animaciones

@keyframes + animation

Una transición necesita que pase algo (el :hover). Una animación se mueve sola.

/* 1. Defines la animación y sus "fotogramas" */
@keyframes moveAnimation {
    0%   { top: 10px;  left: 10px; }
    50%  { top: 500px; left: 200px; width: 200px; height: 200px; }
    100% { top: 10px;  left: 10px; }
}
/* versión corta, con solo principio y fin:  from { … }  to { … } */

/* 2. Se la aplicas a un elemento */
.square-1 {
    position: absolute;
    animation-name: moveAnimation;
    animation-duration: 4s;
    animation-iteration-count: infinite;    /* que se repita siempre */
}
  • Con from/to, al repetirse "salta" de golpe al principio. Con porcentajes (0%, 50%, 100%) puedes hacer que vuelva al sitio y la repetición queda suave.
  • Se usan poco. El caso real típico es el loader (el circulito de "cargando"):
@keyframes loading {
    0%   { transform: rotate(0); }
    100% { transform: rotate(360deg); }
}
.loading {
    width: 30px;
    height: 30px;
    border: 5px solid black;
    border-radius: 90px;                  /* redondo */
    border-right-color: transparent;      /* un trozo sin borde: el hueco que gira */
    animation-name: loading;
    animation-duration: 1s;
    animation-iteration-count: infinite;
}
Así se ve en el navegador

Que el loader salga solo mientras carga algo ya es cosa de JavaScript: lo muestra antes de pedir los datos y lo quita al recibirlos.

19 · Las herramientas del navegador (F12)

Elements y Styles

  • Elements enseña el DOM: el HTML ya interpretado por el navegador. Puedes cambiarlo o borrar cosas para probar, pero no cambias tu archivo: al recargar, vuelve todo. El DOM se usará mucho con JavaScript.
  • Styles enseña todas las reglas que afectan al elemento, ordenadas por especificidad. Las que pierden salen tachadas.
  • Truco: si tu regla no sale ni tachada, es que el selector está mal y nunca llega a ese elemento.
  • El botón de la flechita con un cuadrado (arriba a la izquierda de F12) sirve para hacer clic en algo de la página e ir directo a su código. Muy útil en páginas grandes.
  • Al pulsar el cuadradito de un color en Styles se abre un selector de color para probar.
  • Las reglas en cursiva ("user agent stylesheet") las pone el navegador, no tú. Por ejemplo, los enlaces traen cursor: pointer (la manita). Para cambiarlo, lo sobrescribes con tu CSS.
  • Para el responsive: al cambiar el ancho de la ventana con F12 abierto, arriba a la derecha sale el ancho en px. También está el botón de móvil/tablet para elegir un dispositivo.

Lo que pone el ! de Emmet

  • <!DOCTYPE html>: dice que es HTML5 (antes había que poner otras versiones).
  • <html lang="en">: el idioma de la página. Cámbialo a es.
  • <meta charset="UTF-8">: para que tildes, eñes y símbolos se vean bien.
  • <meta name="viewport" …>: para que la página se adapte al ancho del móvil.
  • Las etiquetas meta dan información al navegador sobre la página; hay muchas más.

<a> o <button>

  • a = enlace: te lleva a otro sitio (otra página o una parte de la misma). Los menús son enlaces.
  • button = botón: hace una acción (añadir al carrito, abrir un menú, enviar un formulario). Se programa con JavaScript.

20 · Responsive: media queries

Qué es responsive (y "mobile first")

  • Responsive = que la página se vea bien en todos los dispositivos. Es el concepto. Las media queries son la herramienta para conseguirlo.
  • Antes se hacían dos webs, una para móvil y otra para escritorio (Twitter tenía mobile.twitter.com). Ya no se hace: es imposible de mantener.
  • Se usan porcentajes para aprovechar el ancho que haya y saltos que cambian el estilo según el tamaño de la pantalla.
  • Mobile first: primero se diseña para el móvil. Es más fácil adaptar poco contenido a una pantalla grande que meter mucho en una pequeña, como mudarse a una casa más grande.
  • Responsive "cutre": display: flex + justify-content: center. Funciona, pero no aprovecha bien el ancho.

Consejo de Héctor: antes de maquetar, comprueba con el diseñador que lo que pide se puede hacer.

@media: cómo se escribe

/* SIN media query: lo común + el MÓVIL */
p {
    color: blue;
    padding: 15px;
    background: pink;
    font-size: 30px;
}

/* desde 480px de ancho en adelante */
@media screen and (min-width: 480px) {
    p {
        font-size: 60px;    /* SOLO lo que cambia */
    }
}

/* desde 600px en adelante */
@media screen and (min-width: 600px) {
    p {
        font-size: 40px;
    }
}
  • screen = en pantalla. Existe print para cuando se imprime (por eso algunas webs salen en blanco al imprimirlas).
  • min-width: 480px = "cuando la pantalla mida 480px o más". Por debajo, esa regla no existe.
  • Si se cumplen varias, gana la de más abajo (sobrescribe).

Solo lo que cambia

  • Una media query no reemplaza toda la regla, solo las propiedades que escribas. El color, el borde y el fondo se mantienen.
  • Error típico de junior: repetir todo otra vez dentro de cada media query.
  • En F12 lo ves: el font-size: 30px de arriba sale tachado y el resto no.
  • Lo que suelen cambiar: tamaños y márgenes. Los colores casi nunca (el fondo del header es azul en móvil y en escritorio).
  • ¿Dónde se ponen? Cada uno a su manera. Héctor las pone todas juntas al final del CSS, una por salto.
  • Hay quien empieza por el escritorio y usa max-width (lo mismo, al revés). Héctor no lo recomienda.

21 · Tarjetas responsive (la tienda)

Por qué no caben dos al 50%

  • El margin va siempre por fuera del tamaño, también con box-sizing: border-box (ese solo mete dentro el padding y el borde).
  • Tarjeta al 50% + 20px de margin a cada lado = más del 50%. Dos así suman más del 100% → la segunda baja.
  • Arreglo "ñapa": bajar al 45%. Funciona, pero los números ya no cuadran.
  • Arreglo bueno: meter cada tarjeta en una caja contenedora. La caja lleva el ancho y un padding (que hace de separación). La tarjeta de dentro lleva el fondo y la sombra, sin margin.
<div class="funko-pill-container">     <!-- ancho + padding -->
    <div class="funko-pill"> … </div>  <!-- fondo + sombra -->
</div>
.main-content {
    display: flex;
    flex-wrap: wrap;
    padding: 20px;
}
.main-content .funko-pill-container {
    width: 100%;          /* móvil: 1 por fila */
    padding: 10px;        /* la separación, POR DENTRO */
}
.main-content .funko-pill {
    background: #f5f5f5;
    height: 100%;         /* todas igual de altas */
    box-shadow: 2px 5px 15px 5px rgba(38,38,38,0.57);
}
@media screen and (min-width: 576px) {
    .main-content .funko-pill-container { width: 50%; }
}
/* … 768px → 33%, 1024px → 25%, 1280px → 20% */
Así se ve en el navegador

"Bienvenido al HTML": meter cajas dentro de cajas. Cuando algo no cuadra, muchas veces la solución es otra caja.

Que todas midan lo mismo de alto

  • Si un título ocupa dos líneas, esa tarjeta crece y las demás quedan desalineadas.
  • Las cajas contenedoras ya se estiran todas a la altura de la más alta (en flex, stretch es lo que pasa por defecto).
  • La tarjeta de dentro no aprovecha ese hueco. Se arregla con height: 100% en la tarjeta.
  • Una altura fija (height: 300px) no es buena idea: si hay más contenido se sale, y si hay menos queda hueco.

El fallo de un compañero

  • Ponía las media queries bien, pero las tarjetas no cambiaban de tamaño.
  • El motivo: la tarjeta de dentro tenía width: 200px. Aunque el padre crezca, el hijo se queda en 200px.
  • Si el ancho lo controla el padre, el hijo no lleva ancho fijo (o lleva 100%).

22 · calc(): "lo que sobre"

Restar píxeles a un porcentaje

En CSS no existe "ocupa lo que sobre". Si una parte mide 300px y la otra tiene que llenar el resto de la pantalla, se calcula con calc():

<div class="container">
    <p class="p1">Hola hola</p>
    <p class="p2">Lo que queda</p>
</div>
.container {
    width: 100%;
    display: flex;              /* uno al lado del otro (los p son block) */
}
.p1 { width: 300px; }
.p2 { width: calc(100% - 300px); }   /* pantalla de 1000 → 700; de 500 → 200 */
  • Deja espacios alrededor del -: calc(100% - 300px).
  • Uso típico: un header con el logo de ancho fijo y el menú ocupando el resto.

23 · Botón de volver arriba

La flecha fija abajo a la derecha

<header class="header" id="header"> … </header>

<div class="scroll-up">
    <a href="#header"><span class="material-symbols-outlined">arrow_circle_up</span></a>
</div>
html { scroll-behavior: smooth; }   /* sube despacio, no de golpe */

.scroll-up {
    position: fixed;     /* pegada a la PANTALLA aunque hagas scroll */
    right: 20px;         /* en vez de left: desde la derecha */
    bottom: 20px;        /* en vez de top: desde abajo */
    transition: transform 1s;
}
.scroll-up:hover {
    transform: rotate(360deg);   /* sin transition no se ve: acaba igual que empieza */
}
.scroll-up span {                /* el tamaño, al ICONO (el span) */
    font-size: 50px;
    color: #575701;
    animation-name: pulse;
    animation-duration: 1s;
    animation-iteration-count: infinite;
}
@keyframes pulse {
    0%   { font-size: 50px; }
    50%  { font-size: 60px; }
    100% { font-size: 50px; }
}
  • Es un enlace (un ancla #header), no un div suelto: te lleva a un sitio. Al ser enlace ya tiene la manita.
  • right/bottom en lugar de left/top: así no tienes que calcular cuánto hay desde la izquierda.
  • El font-size va en el span: el icono es una letra, y en el div no le afectaba.
  • Choque de transform: la animación se hizo primero con transform: scale(), pero entonces el giro del :hover dejó de funcionar. transform es una sola propiedad (scale, rotate y translate juntas): una sobrescribe a la otra. Por eso la animación cambia el font-size y el giro va en el div de fuera.
  • Con JavaScript se suele ocultar hasta que haces scroll.
  • ¿Que tapa el footer al final? Lo sencillo: subirla un poco más (bottom mayor que el footer). Lo exacto ya es JavaScript. "La solución más sencilla suele ser la mejor".
Así se ve en el navegador (baja con la rueda y pulsa la flecha)

24 · Cómo estudiar HTML y CSS

Consejos de Héctor

  • Hay cientos de etiquetas y estilos. No hace falta saberlos todos: lo importante es saber que existen y buscarlos cuando te hagan falta.
  • La mejor referencia: W3Schools, la escuela del W3C (los que deciden cómo funciona la web).
  • Cada navegador aplica estilos por defecto a su manera; por eso la misma página puede verse un poco distinta en Chrome y en Firefox.
  • Edge, Brave y Opera usan Chromium (la base de Chrome) por dentro. Firefox y Safari no.

Apuntes, búsquedas y juniors (clase 19)

  • En programación, los "apuntes" son la documentación: W3Schools tiene la sintaxis y ejemplos de todo. Buscar es normal: Héctor busca cosas de Java a diario porque trabaja en PHP.
  • Lo que sí hay que saber hacer sin mirar al acabar el bootcamp: un for y un if.
  • Saber cuándo usar cada cosa llega con la práctica y viendo cómo se resuelven ejercicios. Les pasa a todos los grupos.
  • Lo que se pide a un junior: código que funcione. Que quede bonito llega después.
  • Prueba cada paso con un console.log antes de seguir. El fallo típico es escribir 7 líneas sin saber si alguna llegó a funcionar.
  • HTML y CSS no los entiende nadie al 100%: a veces la solución es un "apaño" sencillo, y está bien.

La IA, como copiloto

  • No copies código que no entiendas, ni de internet ni de la IA.
  • Úsala para que te explique ("explícamelo como si no supiera nada") o para pedir una pista ("no me lo resuelvas").

Lo esencial

  • El DOM es el HTML vivo, el que ves en F12 → Elements. JS cambia el DOM, no tu archivo.
  • Carga el JS con <script src="main.js" defer></script> en el head. Sin defer, el JS se ejecuta antes de que exista el HTML.
  • Buscar: document.querySelector('selector') da el primero; querySelectorAll, todos (una lista).
  • Selectores como en CSS: .clase, #id, p, [atributo="valor"].
  • Cambiar: textContent (texto), innerHTML (HTML), classList.add/remove/toggle, style.color.

  • Eventos: nodo.addEventListener('click', miFuncion), con la función sin paréntesis.

1 · Cargar JavaScript en la página

Tres formas, como con el CSS

<!-- 1. Dentro del HTML (para probar) -->
<script>
    alert('Hello HTML')     // ventanita del navegador
</script>

<!-- 2. Archivo aparte: LA BUENA -->
<script src="main.js" defer></script>

<!-- 3. La antigua: al final del body -->
    …
    <script src="main.js"></script>
</body>
  • La etiqueta script se abre y se cierra aunque esté vacía.
  • Como con el CSS: mejor en un archivo aparte.

¿Por qué defer?

  • HTML, CSS y JavaScript son lenguajes interpretados: se leen línea a línea, de arriba abajo. (Java o C# son compilados: se convierten antes en otro archivo, como un .exe.)
  • Si el script está en el head, cuando se ejecuta el body todavía no existe, y querySelector no encuentra nada.
  • defer = "estoy aquí arriba, pero ejecútame cuando termines de leer la página".
  • Antes se ponía el script al final del body. Lo verás mucho en código viejo.

2 · HTML, DOM y nodos

El DOM es el HTML vivo

  • HTML = el archivo que escribes tú. Es estático.
  • DOM (Document Object Model) = lo que el navegador ha montado a partir de ese HTML. Es lo que ves en F12 → Elements. Siempre hay DOM, aunque no uses JS.
  • JavaScript cambia el DOM: tu archivo HTML sigue igual. Si recargas, vuelve a como estaba.
  • Cada etiqueta es un nodo. Un nodo es un objeto con todos sus datos: id, href, src, textContent…
  • Es un árbol de cajas dentro de cajas. document es la caja que lo contiene todo, y document.body es el body (existe siempre).
  • Cada nodo sabe quién es su padre, sus hijos y sus hermanos.

Así funciona Amazon: no hay nadie escribiendo una tarjeta de HTML por cada champú. Llega un array de objetos (como los de los ejercicios) y JS crea las tarjetas con un bucle.

addEventListener

const $button = document.querySelector('#clickme')

$button.addEventListener('click', buttonOnClick)   // ← SIN paréntesis

function buttonOnClick() {
    console.log('hiciste clickcito')
}
  • Un evento es algo que pasa por una acción del usuario: un clic, una tecla, entrar en un input…
  • Sin paréntesis: buttonOnClick es "esta función, úsala cuando hagan clic". Con buttonOnClick() la ejecutarías ya, al cargar la página.
  • Se pueden añadir varios addEventListener al mismo botón y se ejecutan todos (aunque lo normal es uno).
  • Cualquier nodo puede tener eventos: un botón, un párrafo, el body…

Las otras formas (no recomendadas): en el HTML, <button onclick="console.log('hola')"> (como poner style=""), o $button.onclick = function () { … }, que solo admite uno: el siguiente pisa al anterior.

El parámetro event

function buttonOnClick(event) {

}
  • Esta función no la llamas tú: la llama el navegador, y le pasa un objeto con información de lo que ha pasado.
  • Es opcional, y se suele llamar event o e.
  • Útil, por ejemplo: con Ctrl pulsado, abrir en pestaña nueva; con una tecla, saber si fue Enter.

7 · Eventos: más cosas (clase 22)

Los eventos son asíncronos

  • Hasta ahora todo el código era síncrono: se ejecuta línea a línea, en orden.
  • Un evento es asíncrono: con addEventListener no ejecutas nada, solo dejas preparado qué pasará cuando el usuario haga algo. Es como meter el pantalón en la cesta: no lo compras hasta que pagas.
  • Por eso la función va sin paréntesis: una función también es una variable (de tipo function), igual que un número.
$button.addEventListener('click', printEventData)       // función con nombre: se lee mejor

$button.addEventListener('click', function (event) {    // función metida dentro: hace lo mismo
    console.log(event)
})

Las dos valen. Héctor prefiere la de nombre en clase porque al leer printEventData ya sabes qué hace sin leer el código de dentro.

this y .value: una función para muchos

const $inputs = document.querySelectorAll('input')

for (const $input of $inputs) {
    $input.addEventListener('input', printValue)   // la MISMA función para todos
}

function printValue() {
    console.log(this.value)    // this = el input en el que estás escribiendo
}
  • .value = lo que hay escrito en un input.
  • this, dentro de la función de un evento, es el elemento que lanzó el evento: el input donde escribes, el botón que pulsas, la carta en la que haces clic…
  • Así no hace falta una función por cada input: como el botón "añadir al carrito" de una tienda, que es el mismo en todos los productos.
  • Ojo: las funciones flecha (() => {}) no tienen su propio this. Para eventos con this, usa function.
  • keypress va antes de que la letra llegue al input (por eso sale una letra por detrás). Con keyup o con input ya está.
Así se ve en el navegador (escribe en cualquier input)

dataset: guardar datos en un elemento

$card.dataset.cardId = card.id         // crea data-card-id="1"
$card.dataset.cardName = card.name     // crea data-card-name="earth"

// …y luego, en el clic:
function cardOnClick() {
    console.log(this.dataset.cardId, this.dataset.cardName)
}
  • Los eventos pasan más tarde. Cuando el usuario hace clic, ya no tienes el array a mano: por eso apuntas en la propia carta lo que vas a necesitar. "Una chuleta para el examen", dice Héctor.
  • En JS se escribe en camelCase (cardId); en el HTML sale con guiones (data-card-id).
  • No es lo mismo que event: event es información del clic (dónde, qué tecla…); dataset son datos tuyos guardados en el elemento.
  • Todas las webs usan atributos data-.

Asincronía

Clase 23 (26/11), con Héctor. Hay cosas que tardan: esperar unos segundos, pedir datos a un servidor… JavaScript no se queda parado esperando: sigue con lo demás y, cuando eso termina, te avisa.

Lo esencial

  • Asíncrono = se hace más tarde. El código de abajo sigue sin esperar (igual que un evento).
  • setTimeout(función, ms): una vez, dentro de X ms. setInterval(función, ms): cada X ms. clearInterval(timer) lo para.
  • Callback: una función que pasas como parámetro para que te la ejecuten cuando terminen.
  • Promesa: algo que terminará más tarde. .then() = salió bien, .catch() = salió mal. Se usan mucho más de lo que se crean.
  • await = "espérate a que termine la promesa". Solo funciona dentro de una async function. Los errores, con try / catch.
  • fetch(url) pide datos a una API → await response.json() los convierte en un objeto de JS.

1 · Tiempo: setTimeout y setInterval

setTimeout: una vez, más tarde

console.log('Empezamos');

setTimeout(sayHi, 5000);   // función SIN paréntesis, y los ms

function sayHi() {
    console.log('Hi');
}

console.log('Terminamos');
  • Sale Empezamos, Terminamos y, 5 segundos después, Hi. El código no se para a esperar.
  • 1000 ms = 1 segundo.
  • Igual que en los eventos, la función puede ir con nombre (como aquí) o metida dentro: setTimeout(function () { … }, 5000).
  • Es como un evento, pero de tiempo. En el juego de memoria lo usáis para dar tiempo a ver la carta.

setInterval y clearInterval: cada X tiempo

let timer = setInterval(sayHi, 1000);  // guardo el "mando"

let i = 0;                  // contador FUERA de la función
function sayHi() {
    i++;
    console.log('Hi nº ' + i);

    if (i === 10) {
        clearInterval(timer);   // lo paro con el mando
    }
}
  • Cuidado: un intervalo sin parar es infinito. En la terminal de Node se corta con Ctrl + C.
  • setInterval devuelve un "mando" (Héctor lo llama timer). Se lo das a clearInterval para pararlo.
  • Ejemplos reales: un reloj que cambia cada segundo, el juego del topo (sale uno cada 3 s).

2 · Callbacks

Callback: "llámame cuando termines"

let users = [];
let maxId = 1;

function addUser(user, callback) {
    setTimeout(function () {      // finge que el servidor tarda 1 s
        user.id = maxId;
        maxId++;
        users.push(user);
        callback(user);           // ← aviso: ¡ya está!
    }, 1000);
}

let manolo = { name: 'Manolo', age: 340 };

addUser(manolo, function (user) {
    console.log('El id de Manolo es: ' + user.id);
});
  • Un callback es una función que se pasa como parámetro y se ejecuta cuando termina lo que tarda.
  • Ya lo hacíais al revés: a addEventListener y a setTimeout les pasáis una función. Aquí recibes tú la función.
  • Se ejecuta como cualquier función: callback(), con paréntesis.
  • Normalmente te llama contándote qué ha hecho: aquí le pasa el usuario con su id nuevo.

¿"callback" es palabra obligatoria?

  • No. Es el nombre de un parámetro, como n1 o user. Podrías llamarlo joseLuis y funcionaría. Se llama callback porque es lo que hace.
  • No hace de callback por llamarse así: lo hace porque tú lo ejecutas con callback(user). Igual que el array no se llena solo: se llena porque escribes users.push(user).
  • Las palabras reservadas (setTimeout, push…) sí tienen que ir exactas: si las escribes mal, explota.
  • Si las cosas tardan, pueden terminar en otro orden. Un servidor puede tardar 1 s o 3 s.
  • Problema: varios callbacks uno dentro de otro se vuelven ilegibles (callback hell). Por eso se inventaron las promesas.

3 · Promesas

Usar una promesa: then y catch

addUser(manolo)                      // ahora devuelve una promesa
    .then(function (user) {          // si salió bien
        console.log('El id de Manolo es: ' + user.id);
    })
    .catch(function (error) {        // si salió mal
        console.error(error);
    });
  • Promesa = "te prometo que terminaré y te diré". addUser ya no recibe un callback: devuelve una promesa.
  • .then() = "cuando termine bien, haz esto". Es lo que sustituye al callback.
  • .catch() = "si sale mal, haz esto". Viene de catch, atrapar el error.
  • Ventaja: puedes encadenar .then().then().then() al mismo nivel, sin meter cosas dentro de cosas.
  • Lo importante es saber usarlas, porque casi siempre las crea otro (por ejemplo fetch).

Crear una promesa: resolve y reject

function addUser(user) {
    const promise = new Promise(function (resolve, reject) {
        setTimeout(function () {
            if (user.name === 'Marcos') {
                reject('Marcos no puede entrar');   // → .catch
            } else {
                user.id = maxId;
                maxId++;
                users.push(user);
                resolve(user);                      // → .then
            }
        }, 1000);
    });

    return promise;
}
  • new Promise(...) crea la promesa. El new es de objetos y clases, que no está en el temario: cópialo tal cual.
  • Recibe una función con dos parámetros: resolve (todo bien) y reject (algo fue mal).
  • resolve → se ejecuta el .then. reject → se ejecuta el .catch. Alguien decidió llamarlos así.
  • A reject se le suele pasar el motivo del error.
  • Fallo de Héctor en clase: puso user.name = 'Marcos' (un solo =) y fallaban los tres. En un if se compara con ===.

4 · Errores: try / catch y throw

Excepción: cuando el código explota

console.log(user);   // ReferenceError: Cannot access 'user'
let user = 'Paco';   //   before initialization

console.log('Paco no mola');   // NO se ejecuta: ya explotó
  • Ese "pete" se llama excepción. Cuando explota, no se ejecuta nada más.
  • Cómo leerlo: tipo de error (ReferenceError) + mensaje + stack trace (la lista de dónde pasó).
  • En el stack trace, lo de node:internal no te importa. Mira tus archivos y el número de línea: el de arriba es donde explotó; los de abajo, quién llamó a esa función.

try / catch: controlar la explosión

try {
    console.log(user);        // intenta esto
    let user = 'Paco';
} catch (exception) {
    console.log(exception);   // si explota, cae aquí
}

console.log('Paco no mola');  // ahora SÍ se ejecuta
  • try = intenta. catch = atrapa el error. El código sigue después.
  • No es para meterlo en todo: las cosas siguen fallando. Tiene usos concretos.
  • Ejemplo: el usuario escribe algo que debería ser un número y no lo es → en vez de explotar, le pides que lo repita.

throw: lanzar tu propio error

function suma(n1, n2) {
    if (isNaN(n1) || isNaN(n2)) {
        throw 'n1 y n2 deben ser numeros';  // exploto y paro
    } else {
        return n1 + n2;
    }
}

console.log(suma(10, 5));   // 15

try {
    console.log(suma('pepe', 'alfonso'));
} catch (err) {
    console.log('Porfaaaa, mete numeroooos');
}
  • throw hace explotar el código a propósito. También se escribe throw new Error('mensaje').
  • Pregunta de Ireneo: ¿para qué, si ya da error? Con console.error + return -1 el código sigue con un resultado falso (−1). Con throw, se para.
  • Cada uno, su responsabilidad: la función que suma solo comprueba que le den números. Quien la usa sabe de dónde vienen y avisa al usuario.
  • isNaN() = "¿no es un número?". Curiosidad: typeof NaN da 'number'.

5 · async / await

await: esperar sin .then

async function addManolo() {
    let manolo = { name: 'Manolo', age: 340 };
    manolo = await addUser(manolo);    // espera y guarda
    console.log('El id de Manolo es: ' + manolo.id);
}

async function addMarcos() {
    try {
        let marcos = await addUser({ name: 'Marcos', age: 17 });
        console.log('Hemos colado un Marcos');
    } catch (error) {
        console.error('La promesa de Marcos dio un error: ' + error);
    }
}

addManolo();
addMarcos();
  • await = "espérate a que termine la promesa y guárdame lo que dé" (lo que se pasó a resolve).
  • Solo vale dentro de una función con async delante. Si no, error: await is only valid in async functions.
  • El error del reject ya no va en .catch(): va en un try / catch.
  • Hace lo mismo que .then, pero se lee mucho mejor, de arriba abajo.

La diferencia entre .then y await

  • .then funciona como un evento: lo dejas preparado y el código de debajo sigue. Un console.log('hola') después sale enseguida.
  • await para esa función hasta que termine la promesa. Lo que está debajo del await espera.
  • Fuera de esa función, el resto del programa sigue normal.

fetch con async / await

async function getCharactersAndPaint() {
    let response = await fetch('https://rickandmortyapi.com/api/character');
    let data = await response.json();   // de JSON a objeto de JS

    let characters = data.results;      // la lista está en "results"
    for (let character of characters) {
        let $div = document.createElement('div');
        $div.innerHTML = character.name + '<br/>';
        document.body.append($div);
    }
}

getCharactersAndPaint();
  • fetch(url) llama a una URL y devuelve una promesa: por eso el await.
  • La response aún no es el dato: hay que pedir response.json() (con otro await).
  • El orden importa: primero response y luego data, porque data usa response.
  • Qué campos trae cada cosa (results, name…) lo dice la documentación de la API, o ábrela en el navegador.
  • Con vuestra API podría ser fetch('http://localhost:3000/mascotas').

La misma, con .then (más fea)

function getCharactersAndPaint() {
    fetch('https://rickandmortyapi.com/api/character')
        .then(function (response) {
            return response.json();
        })
        .then(function (data) {
            let characters = data.results;
            // … pintar igual que arriba
        });
}
  • Hace lo mismo. Lo normal es usar async / await porque se lee mejor.
  • JSON = formato para enviar datos. Se parece mucho a un objeto de JS (viene de JavaScript Object Notation).
  • Una API es una URL que, en vez de una página, te devuelve datos.
